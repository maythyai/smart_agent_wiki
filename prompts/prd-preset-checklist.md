# PRD 预设检查清单（11 点，独立参考文件）

> 本文件是 PRD 提交评审前自查清单的**权威定义**，供 01 PRD（含 planning→engineering 升级模式）与「PRD 评审」gate 引用。与 01「10 点质量自检」互补：10 点覆盖**结构完备性**，本清单覆盖**实证评审提炼的高频 Critical 模式**。
>
> **来源**：某真实项目 11 个版本（v1.171–v1.180）PRD 评审累计闭环的 60 个 Critical 提炼；60 个中约 40 个命中这 11 点。
>
> **示例语境说明**：各点"为何/反例→正例"中的版本号（v1.17x）与业务名词（A2A、AgentCard、epoch 等）是来源项目的示例语境，使用时替换为目标项目对应概念，模式本身通用。
>
> **项目 overlay 机制**：项目若有 `.csp/agent-conventions/PRD-PRESET-CHECKLIST.md`（项目特有沉淀）→ 叠加在本清单之上一起过；评审中新发现的可复用 Critical 模式 → 回流追加进项目 overlay（编号续接），定期 upstream 回本文件。清单是 living document：delta 追加，不推倒重写。

## 01 升级 11 点预设检查清单

> 每次 01 升级 planning→engineering 前**逐条自查**，通过后再提交评审——可减少 60%+ 评审循环。

---

### 1. 可测指标禁 [TBD]

**检查什么**：§1.3 成功指标 + §6 AC 表中所有目标值/阈值必须有具体数值，不得标 `[TBD]`。

**为何**：v1.171 F-02（回滚 RTO 标 [TBD]）、v1.174 C-1（跨 Pod P99 标 [TBD]）——`[TBD]` 进可测指标 → AC 无法 Given-When-Then 判定 → 评审 Critical。

**怎么用**：写 §1.3 每个指标时问"这个值能写进 AC 的 Then 吗？"不能 → 必须给值（即使是保守默认值，如 ≤60s/≥95%/≤1%），不留给 [TBD]。

**反例→正例**：
- ❌ `回滚 RTO | [TBD] | 回滚演练计时`
- ✅ `回滚 RTO | ≤ 60s | 回滚演练计时`

> 边界：非可测的背景性缺口仍可标 `[TBD]`（如业务数据 DAU 未提供）；本条只约束**会进 AC 判定的指标/阈值**。

---

### 2. 分母一致（默认值与目标指标分母不矛盾）

**检查什么**：每个比率型指标（覆盖率/合规率/达成率/拦截率）必须显式声明分母口径；分母与"默认值"不矛盾（默认空清单/不限量 ≠ 100% 覆盖率）。

**为何**：v1.172 F-06（默认不限量配额 vs 处置率 100%）、v1.173 C-3（默认空敏感清单 vs 覆盖率 100%）、v1.174 C-2/C-3、v1.176 C-3（新鲜度合规率分母含删除/stale/归档→结构性拉低）、v1.180 C-2/C-9——分母不定 → 指标不可测或被"未配置"刷分。

**怎么用**：写每个比率指标时声明：分子=?分母=?；默认配置缺失时该主体从分母剔除 + 反向指标单列（"未配 X 租户数"）；不同状态（unknown/partial/删除/归档）与分母关系显式声明。

**反例→正例**：
- ❌ `审批覆盖率 100%`（默认空清单=分母 0 → 恒真）
- ✅ `审批覆盖率 100%（分母=敏感工具调用次数；未配清单租户剔除+反向指标"未配清单租户数"）`

---

### 3. 安全闸门治理生命周期

**检查什么**：所有"安全闸门"（白名单/敏感清单/ACL 规则/门禁规则/撤权触发/配额配置/阈值参数/Replay opt-in 开关）必须有治理生命周期：谁有权变更 → 评审门禁 → 审计事件 → 与配置发布/epoch 联动。

**为何**：v1.172 F-02（安全意图白名单无治理）、v1.173 C-2（敏感工具清单无治理）、v1.176 C-5（ACL/门禁规则无治理）、v1.177 C-4（四子闸门阈值无治理）、v1.180 C-7（authz_policy_changed 无 §5/§6 对应）——安全闸门被误改 → 越权/不合规/绕门禁，且无审计不可追溯。

**怎么用**：识别 PRD 中所有"安全闸门"（凡控制准入/边界/权限的规则）；为每个闸门写：变更需 review_id + 审计事件 `X_changed` + 联动（如配置发布代际失效 / epoch bump）；补 AC 验证"未经评审 → 拒绝 + 审计落盘"。

**反例→正例**：
- ❌ `敏感工具清单可配置`（谁改？审计？联动？）
- ✅ `敏感工具清单新增/移除需评审 + 审计 sensitive_tool_list_changed + 联动配置代际失效（触发在途待审单状态评估）`

---

### 4. known-limit 上界细化到每资源

**检查什么**：每个"不确定性/最终一致/缓存/窗口"资源必须有定量上界（非全局一句"最终一致"），细化到每个资源类型。

**为何**：v1.174 C-5（known-limit 无上界）、v1.175 C-5（archive 保留无上界）、v1.176 C-1（趋势窗口无上界）、v1.177 C-5（六资源中评测/门禁/Replay 三缺上界）——"最终一致"无上界 → 实现侧可无限运行/无限回看/口径漂移。

**怎么用**：扫 PRD 中所有"known-limit / 最终一致 / 窗口 / 缓存 / 保留 / 超时 / 批次"关键词；为每个给定量上界（如 checkpoint ≤1s / 跨 Pod ≤5s / archive ≤90d / 趋势 5 版本 / 聚类 ≤100 条 / Replay ≤90d / 限流 60/min）。

**反例→正例**：
- ❌ `跨 Pod 最终一致（known-limit）`
- ✅ `跨 Pod 最终一致窗口 ≤ 5s（known-limit 上界；窗口期内旧凭据可能有效，单列 known-limit 指标不计入拦截率分母）`

---

### 5. 双模式/多模式校验显式定义

**检查什么**：凡有"双模式/多模式"分支（warn vs block / pass vs degrade / 幂等 vs 重试 / 全缺失 vs 部分缺失 / 入站 vs 出站），必须显式定义各分支的判别条件 + AC 覆盖每个分支 + 标记动作须透传下游效果（标记≠治理，须定义下游行为）。

**为何**：v1.172 C-2（缓存键 vs 相似度查找两套机制混淆）、v1.176 C-1（stale 标了下游照用——标记动作与效果断裂）、v1.177 C-2（partial-warn 无 AC）、v1.180 C-4（双模式术语未定义 + AC 循环引用）——双模式不显式 → 实现侧可能误将 partial 当 block（过严）或当 pass（裸奔）。

**怎么用**：识别所有"if/else 分支 / 双阈值 / 双状态"；为每个分支写判别条件（如"部分维度缺失≠全缺失 → warn 放行+gate_partial 标记透传看板；全缺失 → block 阻断"）；补 AC 覆盖每个分支；标记动作（如 stale/gate_partial/trace_gap）须定义下游行为（降权/透传/单列指标）。

**反例→正例**：
- ❌ `数据缺失→标 unknown，降级 warn`
- ✅ `部分维度缺失（非全缺）→该维度 warn（非 block）+ 记 gate_partial + 发布放行 + 标记透传发布看板单列；全维度缺失 → 阻断（不裸奔）；AC-4.5 覆盖 partial-warn 分支`

---

### 6. 恢复路径覆盖所有异常分支

**检查什么**：恢复路径（附录"恢复路径"节）不只覆盖正向三步（误操作→撤销/重做），必须覆盖**所有异常分支**（含挂起态 SLA + 不可恢复处置 + 竞态 CAS + 误撤权/误熔断/误超时）。

**为何**：v1.175 C-4（审计"不丢"无 fallback）、v1.176 C-6（血缘补录挂起态无 SLA → 100% 覆盖率不可达）、v1.177 C-6（五类异常恢复缺失）、v1.180 C-8（budget 超限"发更大 budget"= 扩权 loophole）——异常标记 + 告警只是检测，恢复才是闭环；挂起态无 SLA → 可永久停留。

**怎么用**：扫 §3.x 异常表每行 → 附录恢复路径必须覆盖；挂起态给 SLA（如"N 天内补录或标不可恢复"）；不可恢复 → 从分母剔除 + 反向指标；恢复动作不引入扩权 loophole（budget 超限→走审批重授权，非自行扩 ceiling）。

**反例→正例**：
- ❌ `budget 超限→重新签发更大 budget token`
- ✅ `budget 超限→拒绝+审计+熔断；重新授权需走评审+审批（审计 delegation_reissued_with_approval），不自行扩 budget ceiling`

---

### 7. HOW 不具名中间件/具名接口

**检查什么**：PRD 只描述 WHAT（做什么/性能要求/安全规格），不具名具体中间件（Nacos/Redis/Sentinel）、具体框架接口名（照搬参考项目的类名/接口名）、具体实现选型（Ed25519/哈希链/append-only）——这些归 03 技术方案。

**为何**：v1.171 F-01（dataId/namespace=Nacos 专属术语）、v1.173 C-1（ApprovalExecutionHandler 照搬参考项目 Java 名）、v1.177 C-1（Ed25519/哈希链具名）、v1.180 C-1（§3.2 具名 Ed25519 + §3.3 具名 append-only/哈希链 与头部"WHAT only"自相矛盾）——HOW 渗入 → 锁定实现选型、与不同技术栈错位、与 PRD 自身声明冲突。

**怎么用**：扫 PRD 中所有具名技术（中间件名/接口名/算法名/数据结构名）；改为 WHAT 描述（"非对称签名"非"Ed25519"；"不可篡改审计"非"append-only 哈希链"；"可插拔执行处理器 SPI"非具体框架类名）；具体选型写进 03 Spec。

**反例→正例**：
- ❌ `执行经 SPI（ApprovalExecutionHandler）对接业务系统`
- ✅ `执行经可插拔执行处理器（SPI）对接业务系统；处理器契约由 03 设计定义`

### 8. 规则-AC-异常三处同步

**检查什么**：补/改 §3.x 业务规则（含强化规则、errata 追加）时，必须同步更新 §6 AC 表（每个新规则有对应 AC）+ §3.x 异常表（规则改变异常行为时同步）——不能只补规则而 §6/异常零对应。

**为何**：v1.176 R2（§3.5 补了 6 条规则但 §6 AC 零对应 → "规则声称闭环而验收真空" → 2 轮重审）、v1.180 R2 C-9（分母修正 bleed 到邻行指标）——只补规则不补 AC → 评审必拒；分母修正 bleed 到邻行 → 新引入分母矛盾。

**怎么用**：每写一条强化规则 → 立即在 §6 AC 表补对应 AC（引 finding 编号回溯）→ 检查 §3.x 异常表是否需同步；分母修正只改目标行，不 bleed 到邻行（子集指标的分母应窄于父集指标，不能等宽）。

**反例→正例**：
- ❌ §3.5 补"C4 出站签名" → §6 无 AC-1.4 → 验收真空
- ✅ §3.5 补"C4 出站签名" + §6 补 AC-1.4（出站：本 Agent 私钥签+携带 epoch）+ §3.1 异常表同步出站分支

### 9. 信任模型 sym/asym 按场景

**检查什么**：凡涉及签名/鉴权的功能，必须显式定义信任模型——对称（HMAC，验证方持密钥）还是非对称（私钥签/公钥验）——按场景选择：内部/intra-org 可对称，跨组织/cross-org 必须非对称。

**为何**：v1.178 C-1（跨组织用对称 HMAC → 验证方须持私钥 → 结构性信任黑洞，公开端点"签名保证可信"自相矛盾）、v1.179 C-3（出站信任黑洞）、v1.180 C-6（sym/asym 模型未定义）——跨组织用对称密钥 → 密钥分发链路不可行 → 信任模型崩塌。

**怎么用**：识别 PRD 中所有签名/鉴权场景；标注场景（intra-org/cross-org）；intra-org → 对称 HMAC（复用既有机制）；cross-org → 非对称签名（公钥嵌入 + out-of-band trust_store）；trust_store 生命周期（add/remove 公钥需评审+审计）。具体算法选型归 03。

**反例→正例**：
- ❌ 跨组织 AgentCard 用 HMAC-SHA256 签名（验证方须持密钥 → 跨组织不可行）
- ✅ 跨组织 AgentCard 用非对称签名（私钥签/公钥验 + trust_store 受信公钥集合 out-of-band 分发）

### 10. 入站 + 出站对称覆盖

**检查什么**：凡双向通信（请求+响应/委派+通知/出站+入站），信任/鉴权/签名须**对称覆盖**——不能只覆盖入站（验远端），出站（本端签+携带凭据）也必须有 AC。

**为何**：v1.179 C-3（委派 POST 出站鉴权/签名未定义，仅入站覆盖）、v1.180 C-5（入站+出站对称声明但 §6 AC 只测入站，出站零 AC）——只验入站不签出站 → 远端无法验证请求来源 → 出站信任真空。

**怎么用**：识别所有双向通信（委派 POST / 通知 webhook / 卡片发布）；为每个方向写鉴权规则 + AC（入站验远端签+新鲜度凭据；出站本端签+携带凭据）；AC 表覆盖两个方向。

**反例→正例**：
- ❌ §3.1 委派 POST 鉴权只写"验远端 AgentCard"（入站）→ 出站零覆盖
- ✅ §3.1 入站（验远端签+epoch）+ 出站（本 Agent 私钥签+携带 epoch）+ AC-1.4 出站签名

### 11. PRD 不具名实现选型 + 分母不 bleed 邻行

**检查什么（两点合并）**：
- (a) PRD 不具名实现选型（Ed25519/哈希链/append-only/Redis——归 03；PRD 描述 WHAT：非对称签名/不可篡改/至少一次）；
- (b) 分母修正不 bleed 到邻行指标（修 C2 拦截率分母时，不把覆盖率指标分母也改了——子集指标的分母应更窄，不能与父集指标同分母）。

**为何**：v1.180 C-1（§3.2 具名 Ed25519 + §3.3 具名 append-only/哈希链 与"WHAT only"自相矛盾）+ v1.180 R2 C-9（为修 C2 把覆盖率分母误改为父集口径，与 §1.3 原定义冲突——分母 bleed）——具名实现选型 = HOW 渗入（第 7 点的细化）；分母 bleed = 修正副作用引入新矛盾。

**怎么用**：
- (a) 写 PRD 时用 WHAT 描述（"非对称签名"非"Ed25519"）；选型写进 03 Spec；§3.x errata 覆盖原文 stale 具名文本。
- (b) 修分母时只改目标指标行；检查邻行指标分母是否被误改（子集指标的分母应 ≤ 父集指标分母，不能等宽）。

**反例→正例**：
- ❌ §3.2 "签名：Ed25519"（具名实现选型）+ 鉴权覆盖率分母="所有 A2A 边界校验次数"（bleed 到边界违反拦截率分母）
- ✅ §3.2 "签名：非对称（私钥签/公钥验，选型归 03）" + 鉴权覆盖率分母="A2A 请求次数"（子集，窄于边界违反拦截率的"边界校验次数"分母）

## 使用方式

- **01 升级模式（planning→engineering）**：写完 PRD draft → **逐条过 11 点**（+ 项目 `.csp/agent-conventions/PRD-PRESET-CHECKLIST.md` overlay 条目，若存在）→ 通过后再提交「PRD 评审」。预期效果：60%+ Critical 在自查阶段消除，评审循环从平均 1.5 轮降至 ≤1.2 轮。
- **PRD 评审（01 gate）**：reviewer 先按 11 点做机械式 fast scan（模式匹配，命中直接出 finding），再进多视角深审。
- **回流**：评审发现的新 Critical 模式（11 点之外、可复用）→ 追加进项目 overlay（编号续接 12+）；跨项目复现的 → upstream 回本文件。
