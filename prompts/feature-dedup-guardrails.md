# 功能去重护栏（Feature Dedup Guardrails）——新功能开发前置约束·通用方法论

> **定位**：开发期（05 实施）的**功能准入护栏**，与规划期的 `product-design-convergence.md`（收敛闸门）互补——收敛闸门裁决"该不该做"，本护栏约束"怎么做才不产生重复冗余"。
>
> **通用性**：本文档是**项目无关的方法论**。所有项目特定概念（支柱名称、基础设施通道、元数据源、次级入口形式）均为占位符，由各项目在 `AGENTS.md`/`.csp/product-spec/` 中实例化。不绑定任何具体技术栈或业务域。
>
> **可直接粘贴**：§七 提供可拼入任何新功能开发 prompt 的「前置约束任务描述片段」。

## 一、通用问题定义

### 1.1 什么是"功能重复冗余"

功能重复冗余 = **同一用户能力/同一数据/同一业务动作，在系统中存在 ≥2 处独立实现或入口**，且这些实现/入口之间无派生关系（各自维护、各自漂移）。

四种典型形态（通用分类，不绑定具体项目）：

| 形态 | 通用定义 | 典型症状 |
|------|---------|---------|
| **R1 平行页面/入口** | 同一用户任务有 ≥2 个独立页面或导航入口 | 两个路由做同一件事；新旧入口并存 |
| **R2 旁路实现** | 新代码绕过既有统一基础设施，自建平行逻辑 | 不走统一发布/账号/合规/审计通道，自己实现一套 |
| **R3 元数据多副本** | 同一份数据（后端已提供或单一源已定义）被复制成 ≥2 份静态副本 | 前端硬编码第二份配置数组；多处维护同一枚举 |
| **R4 语义重叠功能** | 两个功能名/概念语义高度重叠，用户无法区分 | 同义动词+名词组合命名的两个功能；谱系交叉 |

### 1.2 为什么会发生（根因，通用）

功能重复冗余**不是偶然写错，而是缺少开发期准入约束的必然结果**：

1. **无查重前置**：开发新功能前不检索全仓库是否已有同类能力 → 直接新建平行实现。
2. **无归属原则**：功能不强制映射到核心支柱/限界上下文 → 任何新功能都能"自成一派"占一级入口。
3. **基础设施不可见**：开发者不知道已有统一通道（发布/账号/合规/元数据源）→ 顺手自建旁路。
4. **导航准入无门禁**："新增一级导航"成为新功能的默认解法 → 入口膨胀、边界不排他。
5. **无完成自检**：交付时不验证"同类能力全仓库仅一处实现" → 重复 silently 滋生。

### 1.3 边界定义（什么算"同一能力"，什么不算）

判定"是否重复"的通用边界，避免误判（把合理的相似当重复）或漏判（把实质重复当不同）：

| 判定维度 | 算"同一能力"（重复候选） | 不算重复（合理共存） |
|---------|----------------------|-------------------|
| **用户任务** | 完成的是同一个用户目标（如"把内容发到平台"） | 不同用户目标（"创作"vs"发布"vs"分析"） |
| **输入输出** | 输入类型 + 输出结果实质相同 | 输入或输出有本质差异 |
| **数据源** | 消费/产出同一份数据实体 | 不同数据实体 |
| **业务动作** | 触发同一业务动作（同一动词+同一宾语） | 不同动作或不同宾语 |
| **归属上下文** | 属于同一限界上下文/支柱 | 属于不同支柱且职责清晰 |

> **裁决原则**：≥3 个维度判定为"同一能力" → 重复候选，必须归并；1-2 个维度 → 记录"疑似"，人工确认；0 个 → 合理共存。边界模糊时以"用户是否需要区分这两个入口"为最终判据——用户不需要区分 = 重复。

## 二、六条开发前置约束（通用）

> 每条约束 = 一个准入检查。开发任何新功能前逐条执行，在产出中给出结论。约束本身项目无关；括号内是各项目的实例化点。

### 约束 1：定位查重（必须，对应 R1/R4）

**规则**：开始实现前，用**域词典**（同义动词 + 名词组合）grep 全仓库，检索是否已有同类功能入口（页面/组件/API/路由）。

**通用方法**：
```bash
# 1. 从功能名提取动词+名词关键词及其同义词
# 2. 全仓库检索既有入口
grep -riE "<动词>|<synonym1>|<synonym2>" \
  <前端路由目录> <API 路由目录> <功能清单 docs/FEATURES.md> <PMS .csp/product-spec/> \
  --include='*.ts' --include='*.tsx' --include='*.py' --include='*.md'
```

**裁决**：
- 命中同类入口 → **归并增强既有入口**，禁止新建平行页面。
- 未命中 → 记录"经查重无同类"，方可新建。

**实例化点**：域词典维护在 `DOMAIN-THESAURUS.md`（动词→名词→既有功能对照表）；检索目录由项目结构决定。

### 约束 2：支柱归属（对应 R1/R4）

**规则**：明确本功能属于哪个**核心支柱/限界上下文**（项目自定义，来自 `AGENTS.md`/`STRATEGY.md`/`.csp/product-spec/`）。

**裁决**：
- 属于某支柱 → 归入该支柱的既有入口结构。
- **不属于任何支柱** → 默认砍掉或降级为既有功能的子能力，**不新增顶层导航**。
- 需要新建支柱 → 必须先走战略论证（修订 AGENTS.md/STRATEGY.md），不能在开发期自封支柱。

**实例化点**：支柱清单（如"采集/创作/发布/分析"或项目自己的 N 支柱）；支柱与导航分组的映射。

### 约束 3：复用既有基础设施（对应 R2）

**规则**：核心业务动作必须走**统一基础设施通道**，禁止在新页面/新模块内自建旁路 API 或重复实现。

**通用识别**（项目实例化具体通道）：
| 基础设施类型 | 通用要求 |
|------------|---------|
| 业务动作通道（如发布/支付/通知） | 走统一服务，复用其追踪/校验/适配逻辑，不自建 |
| 身份/凭证体系 | 走统一账号/鉴权体系，不自建第二套凭证管理 |
| 合规/审计/校验 gate | 走统一 gate，不绕过 |
| 数据访问层 | 走统一 Repository/DAO，不在 Router/Service 直连数据源 |

**裁决**：发现新代码自建了上述任一通道的平行实现 → 重构为复用既有通道；既有通道缺失能力 → 扩展通道（单一处），不在消费方各建一套。

**实例化点**：项目的统一通道清单（发布通道/账号体系/合规 gate/审计追踪等的具体服务名）。

### 约束 4：元数据单一事实源（对应 R3）

**规则**：后端/单一源已提供的元数据（平台列表/配置项/枚举/规格等），前端及其他消费方**禁止再硬编码第二份静态副本**，一律从既有数据源消费（API/常量模块/配置中心）。

**通用方法**：
```bash
# 检索某元数据是否已有单一源
grep -riE "<元数据名>" <后端 schema/API> <前端常量目录> --include='*.ts' --include='*.py'
# 若前端存在与后端同语义的硬编码数组/对象 → R3 违规
```

**裁决**：
- 已有单一源 → 消费方 import/请求该源，删除本地副本。
- 无单一源 → 先建立单一源（后端 API 或共享常量模块），再消费。
- 派生允许（从单一源 filter/map），**平行复制禁止**。

**实例化点**：项目的元数据单一源位置（后端 config 路由/共享常量包/配置中心）。

### 约束 5：导航准入（对应 R1）

**规则**：新增**侧栏/主导航可见项**必须通过三问；任一不过 → 收进**次级入口**（命令面板/全局搜索/折叠菜单/设置内），不占主导航。

**导航准入三问**（通用）：
| 问题 | 通过标准 | 不通过的处置 |
|------|---------|------------|
| Q1 独立任务域？ | 代表一个不能归入现有导航节点的独立用户任务域 | 嵌套到现有节点 |
| Q2 高频使用？ | 使用频率 ≥ 每周一次（核心路径） | 降级到次级入口 |
| Q3 无同类入口？ | 现有导航无同类/同义入口（约束 1 查重通过） | 归并到同类入口 |

**导航预算**：主导航顶层节点数有上限（建议 5-7，项目自定义）；超预算时**冻结新增**，先做收敛（合并/降级/砍）。

**实例化点**：导航预算值；次级入口的具体形式（命令面板/搜索/折叠菜单）。

### 约束 6：完成前自检（对应全部 R）

**规则**：功能完成前，grep 验证**同类能力全仓库仅一处实现**；输出「归并了什么 / 复用了什么 / 新增了什么」三行清单。

**通用自检**：
```bash
# 同类能力实现唯一性验证
grep -riE "<能力关键词>" <代码目录> --include='*.ts*' --include='*.py' | grep -vE "test|spec|__tests__"
# 期望：实现处仅 1 个（其余为引用/测试/文档）
```

**产出格式**（每个新功能交付时必附）：
```markdown
### 功能去重自检 — <功能名>
- 归并了什么：<归并到的既有入口/能力，或"无（查重无同类）">
- 复用了什么：<复用的基础设施通道/元数据源，或"无（无需复用）">
- 新增了什么：<真正新增的代码/入口，及其支柱归属>
- 唯一性验证：grep <能力关键词> → 实现处 N 个（期望 1）✅/❌
```

**裁决**：唯一性验证 ❌（实现处 >1）→ 阻断交付，回到约束 1-4 归并。

## 三、与流程其他环节的集成（不重复劳动）

| 环节 | 关系 | 分工 |
|------|------|------|
| `product-design-convergence.md`（规划期闸门） | **上游** | 收敛闸门在 roadmap→PRD 间裁决功能"该不该做/归哪个支柱/导航准入"；本护栏在开发期约束"怎么做不重复"。收敛闸门的支柱映射/导航预算/立项查重（N8）是本护栏约束 1/2/5 的规划期版本。 |
| `05-implementation.md`（开发期） | **宿主** | 本护栏注入 05 的「单 Task 实施纪律」，作为每个新功能 TDD 循环前的前置 gate。 |
| `prevention-norms.md`（编码规范+CI 门禁） | **互补** | N8 立项查重 = 约束 1；N3 单一事实源 = 约束 4；N1 路由必须注册 + 导航准入 = 约束 5。本护栏是开发期人工执行版，prevention-norms 的 G1-G5 是 CI 机器拦截版。 |
| `automation-validation.md`（机器门禁） | **机器化** | G-NAV（导航预算）= 约束 5 的机器版；G-DUAL-NAV（多导航源）= 约束 4/5 的机器版；G-POS（定位漂移）= 约束 2 的机器版。 |
| `product-critic-review.md`（事后批评） | **事后兜底** | 镜头 A（重复与冗余 A1-A5）= 本护栏 R1-R4 的事后检测版。护栏是事前预防，critic 是事后挑刺。 |

**去重契约**：约束 1/2/5 的判定结果可被收敛闸门/critic 引用，不重复跑；约束 3/4 的既有通道清单以 CMS（`.csp/code-spec/`）为权威，不在各功能开发时重新发现。

## 四、预防措施的层级（事前 > 事中 > 事后）

| 层级 | 措施 | 载体 | 强制力 |
|------|------|------|--------|
| **事前（规划期）** | 立项查重 + 支柱归属 + 导航预算裁决 | convergence 闸门 | 不通过不进 PRD |
| **事中（开发期）** | 六条前置约束 + 完成自检 | 本护栏（05 注入） | 自检 ❌ 阻断交付 |
| **事中（CI）** | G1-G5 编码门禁 + G-POS/G-NAV/G-DUAL-NAV 治理门禁 | prevention-norms + automation-validation | ERROR 阻断合并/发布 |
| **事后（审计期）** | critic 镜头 A 重复检测 + e2e L4 孤儿路由 + gap 联动检查 | 各审计提示词 | findings 回流 roadmap |

> **核心原则**：重复冗余的预防成本随阶段递增——规划期砍一个重复功能 = 0 成本；开发期归并 = 低；CI 拦截 = 中；事后审计发现再重构 = 高（已扩散）。本护栏把拦截点前移到开发期，是成本最优的防线。

## 五、反模式（通用，硬禁止）

| 反模式 | 症状 | 正确做法 |
|--------|------|---------|
| **先建后查** | 新页面建好了才想起查重 | 约束 1 查重是实现的**第一步**，不是最后一步 |
| **平行页面** | 同一任务两个路由并存 | 归并到单一入口，旧入口走 deprecation TTL（prevention-norms N7） |
| **旁路 API** | 新功能自建一套发布/账号/校验逻辑 | 约束 3 复用统一通道；通道缺能力则扩展通道单一处 |
| **静态副本** | 前端硬编码后端已有的元数据数组 | 约束 4 从单一源消费，删除本地副本 |
| **默认加导航** | 新功能=新一级导航项 | 约束 5 三问，不过则收次级入口 |
| **自封支柱** | 开发期自己定一个新功能域 | 约束 2 新支柱须走战略论证修订 AGENTS.md |
| **无自检交付** | 交付时不验证唯一性 | 约束 6 grep 验证 + 三行清单，❌ 阻断 |
| **"将来可能要"的抽象** | 为假想的复用提前建第二套 | 只建当前 Spec 要的；复用走既有通道 |

## 六、边界与豁免（避免过度约束）

护栏不是教条，以下情况**不算重复**，不强制归并：

| 豁免情形 | 理由 |
|---------|------|
| 不同支柱的同名动作（如"创作预览"vs"发布预览"） | 用户任务域不同，输入输出不同 |
| 只读展示 vs 可写操作（如"查看配置"vs"编辑配置"） | 行为本质不同 |
| 不同平台的适配实现（共享接口，各自实现） | 接口单一，实现按平台分化是合理的（适配器模式） |
| 测试/mock 中的副本 | 测试隔离需要，非生产重复 |
| 已走 deprecation TTL 的旧入口（过渡期） | 有明确退役计划，非永久重复 |

> 豁免必须在「完成自检」清单中显式声明（"新增了什么 + 为何不算重复"），不沉默豁免。

## 八、风格与边界

- **通用方法论**：本文档不绑定任何项目/技术栈/业务域；所有具体名称是占位符，由项目实例化。
- **事前预防优先**：护栏的价值在"拦截于开发期"，不是"事后审计发现"。
- **裁决而非建议**：每条约束的产出是明确裁决（归并/复用/新增/阻断），不是"建议考虑"。
- **与收敛闸门衔接**：规划期已被 convergence 砍掉/归并的功能，开发期不应复活；本护栏约束 1/2/5 是 convergence 裁决的开发期执行。
- **默认中文**，代码/路径/命令保留英文；表格优先。

---

将本护栏的六条前置约束注入新功能开发流程：开发任何新功能前，先执行约束 1（定位查重）→ 约束 2（支柱归属）→ 约束 3（复用基础设施）→ 约束 4（元数据单源）→ 约束 5（导航准入），再进入 TDD 实现；完成前执行约束 6（唯一性自检 + 三行清单）。每条约束在产出中给出明确结论与裁决，命中重复即归并，不新建平行实现。边界豁免须显式声明。
